## Note: Usage of AI

This is year 2026, many developers (and non-developers) use agentic AI for application development, however the quality and reliability of the code generated by these agentic AI varies a lot. C++ code is a particularly dangerous place, and even though humans are also bad at writing safe C++ code, we at least have the principle of code ownership.

The project follows this guidelines that apply for any contributions including myself (see examples below):
- No C++ LLM-generated (or AI-generated in general) code can be submitted to the app
  - One exception is adding new tests to already existing test suites. Editing existing tests and adding completely new tests (e.g. for new functionality) should still be done only by human contributors without using AI-generated code.
- Kotlin code still must be mostly authored or edited by humans. Using LLMs is permitted while done in moderation and thoroughly reviewed by a human before bringing it to the repository (both merge requests or submitting directly).
- XML layouts are permitted to be created or edited by LLM, but should be reviewed by humans. 
- All other code and configs may only be authored by humans.
- It is permitted to use any types of AI to analyze the code, generate reports and suggestions. Automated creation of Issues is also permitted in moderation, but not merge requests (Pull Requests).

Examples to demonstrate the difference:
- There is a function that is covered by unit tests. It is OK to use LLM to add new tests for the function to the same test suite.
- There is a function that is not covered by unit tests. It is not OK to use LLM to add tests to this function, they should be authored manually.
- A contributor authored a new UI functionality in Kotlin using LLM-driven code completion for assistance, or used Agentic AI to research the existing logic and suggest solutions (but no code was generated by the agentic-AI). This feature is permitted to be added.
- Agentic AI was used to add a new UI functionality, prompted by a contributor. This functionality is not allowed to be added.

## What Is this App About

Automatic file backup using Wi-Fi, without the need of using cloud or set up your own private cloud.

1. Install the host app on your PC that works in background.
1. Pair with your phone app.
1. Set up what you want to back up.
1. Now every time your phone is in the same Wi-Fi network with your PC and the PC is on, your files will be backed up to the PC in the background.

The backups are fully end-to-end encrypted (including all file meta-data and individual file sizes), the information about the used protocols can be found at the bottom of the page.

The file transfer can be safely interrupted and resumed at any point (including mid huge file), the used storage is crash-proof (thanks to LMDB as the local storage).

## Details About Used Protocols

Noise_XX_25519_ChaChaPoly_BLAKE2b is used for exchanging paring information, and its handshake hash used to derive short authentication string (SAS) to confirm the pairing.

Static keys for Noise protocol are generated per unique pairing, and re-generated even if the same host and client application are re-paired.

Noise_KK_25519_ChaChaPoly_BLAKE2b is used for file exchange, however accompanied with sending a connection ID in plain-text (static ID generated based on public keys of this device pairing).

Both Noise implementation is covered with tests, including tests comparing it with Rust implementation from [noiseexplorer.com](https://noiseexplorer.com))

Used primitives (by [monocypher](https://monocypher.org/manual/aead):
- X25519 for public key cryptography
- BLAKE2b for hashing
- XChaCha20/Poly1305 for authenticated symmetrical encryption

A custom UDP protocol similar to Bonjour protocol (but much simpler and more strict) is used for network service discovery (NSD).

The file transfer is split in equally sized chunks with equally sized number of chunks between answers, both padded, which allows hiding the number of files and their sizes being transmitted.

All the protocols ensure the sizes of the messages when possible, or otherwise set maximum allowed sizes to variable sized data passed over network, rejecting anything that doesn't fit.

### What is protected and what is not
- An attacker trying to perform a man-in-the-middle (MITM) attack during device pairing procedure needs to correctly forge keys for a handshake to produce the same 6 digit SAS on both sides. This is without knowing in advance the keys of the other party (which are re-generated each try). This makes the MITM attack highly unlikely.
- An attacker connected to the same network as the client application can determine that the device is using this application (by seeing the NSD requests).
- An attacker trying to intercept the file exchange communication is not able to determine the content of the data by the design of the protocol. Trying to tamper with the data in flight or repeating the data will result in authentication failure and stop of transmission.
- An attacker, who has been in the same network with the host and probed the host, or saw the client and the host application exchanging information, can then create an application in other Wi-Fi networks to identify the client by answering the NSD requests.
- An attacker who is in the same Wi-Fi network with the host and the client during the file exchange can roughly estimate the total size of all the files exchanged (sum of the sizes, but not individual sizes). However, chunk padding, potential resume of partial transfer, and metadata of individual files, all complicate the estimation.
- An attacker can not forge a host application that can trick the client to exchange the files with it. At most, first chunks of encrypted data will be sent which could not be decrypted, but the connection will be closed as soon as the host is required to answer the status.
- An attacker can not forge a client application that would allow uploading files to the host application, the connection will be dropped as soon as the first file transfer is attempted after the failed handshake.
